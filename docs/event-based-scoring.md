# Event-Based Scoring Model

This document describes the event-based data model for match scoring. Both sensors and the web UI submit events; the backend derives scores from valid events.

## Motivation

The previous model stored goals directly in a `goals` table. This worked for basic tracking but had limitations:

- No audit trail for corrections or false sensor detections
- No way to distinguish sensor goals from manual web entries
- No deduplication for sensor retries
- Score was mutable shared state rather than a derived value

## The `match_events` Table

All scoring actions are recorded as events in an append-only log.

| Column             | Type                | Description                                                  |
| ------------------ | ------------------- | ------------------------------------------------------------ |
| `id`               | bigint              | Auto-generated primary key                                   |
| `created_at`       | timestamptz         | When the event was recorded                                  |
| `match_id`         | bigint              | The match this event belongs to                              |
| `type`             | match_event_type    | Kind of event (see below)                                    |
| `team_id`          | bigint              | Team the event applies to                                    |
| `player_id`        | bigint (nullable)   | Player who scored, if known                                  |
| `source`           | match_event_source  | Origin: `sensor`, `web`, or `system`                         |
| `source_id`        | text (nullable)     | Identifier of the source (sensor device ID or user ID)       |
| `dedupe_key`       | text (nullable)     | Client-generated key for deduplication; unique when provided |
| `status`           | match_event_status  | Current status: `valid`, `invalid`, or `removed`             |
| `goal_time`        | interval (nullable) | Elapsed match time when the event occurred                   |
| `metadata`         | jsonb (nullable)    | Extensible payload for additional event data                 |
| `related_event_id` | bigint (nullable)   | References another event this one corrects or supersedes     |

### Event Types

| Type                | Description                                         |
| ------------------- | --------------------------------------------------- |
| `goal_detected`     | A goal was scored (from sensor or manual web entry) |
| `goal_removed`      | A previously recorded goal was removed              |
| `score_reset`       | The score was reset (e.g. after a dispute)          |
| `manual_correction` | A manual correction was applied to a previous event |

### Event Sources

| Source   | Description                                                |
| -------- | ---------------------------------------------------------- |
| `sensor` | Event originated from a Pico W break-beam sensor           |
| `web`    | Event was submitted via the web UI                         |
| `system` | Event was generated by the system (e.g. auto-finalization) |

### Event Statuses

| Status    | Description                                      |
| --------- | ------------------------------------------------ |
| `valid`   | Event counts toward the score                    |
| `invalid` | Event does not count (e.g. false sensor trigger) |
| `removed` | Event was superseded by a later correction       |

## Score Derivation

The current score for a match is derived by counting valid `goal_detected` events per team:

```sql
SELECT * FROM get_match_score(<match_id>);
```

This returns one row per team with their score. Only events with `type = 'goal_detected'` and `status = 'valid'` are counted.

## Deduplication

Sensors may retry requests due to network issues. To prevent duplicate goals, sensors include a `dedupe_key` (e.g. a UUID or device-generated sequence). The database enforces uniqueness on this key via a partial index:

```sql
CREATE UNIQUE INDEX match_events_dedupe_key_key
  ON match_events(dedupe_key)
  WHERE dedupe_key IS NOT NULL;
```

Events with `dedupe_key = NULL` (typical for web submissions) are not subject to this constraint.

## Corrections and Audit Trail

When a goal needs to be invalidated (e.g. a false sensor trigger), the original event is marked `invalid` and a `manual_correction` event is inserted with `related_event_id` pointing to the original. This preserves the full history:

```
1. goal_detected (sensor, valid)     <- original sensor event
2. manual_correction (web, valid)    <- correction, related_event_id = 1
3. goal_detected (sensor, invalid)   <- original event marked invalid
```

## Realtime Updates

The `match_events` table is published to `supabase_realtime`. Clients subscribe to `INSERT` and `UPDATE` events filtered by `match_id` to receive live score updates.

## Row-Level Security

| Policy                                                   | Action | Condition                              |
| -------------------------------------------------------- | ------ | -------------------------------------- |
| Admin users                                              | ALL    | `is_admin() = true`                    |
| Authenticated users can view match events                | SELECT | Always                                 |
| Authenticated users can record events for active matches | INSERT | Related match has `in_progress = true` |
| Authenticated users can update events for active matches | UPDATE | Related match has `in_progress = true` |

## Data Flow

```
Pico W Sensor                    Web UI
     |                              |
     | POST match_events            | POST match_events
     | (source=sensor,              | (source=web,
     |  dedupe_key=...)             |  dedupe_key=NULL)
     v                              v
  +-----------------------------------+
  |        match_events table         |
  |  (append-only event log)          |
  +-----------------------------------+
                  |
                  | Supabase Realtime
                  v
  +-----------------------------------+
  |     Solid.js Frontend             |
  |  - Subscribes to match_events     |
  |  - Derives score via              |
  |    get_match_score() or local     |
  |    filtering of valid events      |
  +-----------------------------------+
```

## Migration Path

The `goals` table remains in the schema for now. Follow-up issues will:

1. Migrate the frontend to read from `match_events` instead of `goals`
2. Update sensors to POST to `match_events` instead of `goals`
3. Deprecate and eventually remove the `goals` table
